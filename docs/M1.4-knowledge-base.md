# M1.4 Historical Defect Knowledge Base

## Pipeline

```
Kaggle CSV files -> load -> clean -> MySQL (historical_defects, defect_comments)
                                  -> chunk -> embed (sentence-transformers) -> ChromaDB
Query text -> embed -> ChromaDB (nearest chunks) -> group by defect -> MySQL (full records) -> ranked defects
```

Code: `backend/app/kb/` (`loaders`, `cleaning`, `chunking`, `embedder`, `vector_store`, `retrieval`, `build`, `search`, `evaluate`).

## Datasets used

| Source | Files | Notes |
|---|---|---|
| Apache | `Issues.csv`, `Comments.csv`, `Issuelinks.csv` | Jira data. `Changelog.csv` is not used. |
| Mozilla | `mozilla_bug_report_data.csv` | Bugzilla data |
| Eclipse | `eclipse_bug_report_data.csv` | Bugzilla data |

The loader finds these files anywhere under `backend/data/`, so both zips can be unzipped there as they are.
Column-to-schema mapping is in the M1.2 document, section 7.4.

**Apache selection:** issue type `Bug` with status category `done` (resolved or closed). Because the file is very large,
a sample is loaded (default 10,000, set with `APACHE_SAMPLE_SIZE` or `--apache-sample`). Issues linked as duplicates
are included first (up to 300 pairs) so retrieval can be tested against known answers.
**Mozilla and Eclipse:** all rows with a usable description.

## Cleaning rules

1. Normalise line endings, remove control characters, trim trailing spaces, collapse runs of blank lines.
2. Apache text only: remove Jira markup (`{code}`/`{noformat}` markers, `[~user]` mentions, `!image.png!`, `h2.` headings).
3. Drop records whose description is shorter than 20 characters.
4. Drop repeated (source, bug id) pairs.
5. Move stack traces (Java, JavaScript, Python, gdb-style) out of the description into their own field.
   At least two consecutive frame lines are required, so ordinary sentences containing "at" are not treated as traces.
6. Dates are parsed to UTC; unreadable dates become empty.

## Chunking strategy

Each defect becomes several chunks, one kind of content per chunk, so a hit shows what matched.
Windows are about 1000 characters with 150 characters of overlap, cut at paragraph, line, sentence or word boundaries.
1000 characters fits within the 256-token input limit of the default embedding model.

| Chunk type | Content | Limit per defect |
|---|---|---|
| description | title + description | 4 chunks |
| stack_trace | extracted traces | 2 chunks (no overlap) |
| comment | comments of 40+ characters, first window of each | 5 chunks |
| resolution | resolution label + closing note | 1 chunk |

The Mozilla and Eclipse files have no comments or fix notes, so they only produce description and stack_trace chunks.
For Apache, the **last comment on a resolved issue is used as the resolution note**. This is a heuristic, not a field in the data.

## Index and metadata

ChromaDB collection `historical_defects`, cosine similarity. Chunk id: `<defect id>:<chunk type>:<number>`.
Metadata on every chunk: `defect_id` (MySQL id), `source`, `project`, `component`, `chunk_type`, `chunk_no`,
`status`, `resolution`, `severity`, `priority`, `duplicate_of`, `created_at`. Missing values are stored as empty strings.
The embedding model name is stored on the collection; building with a different model requires `--reset`.

## Retrieval

`search_similar()` embeds the query, fetches the nearest chunks (optionally filtered by `source`), keeps the best chunk per defect,
loads the full records from MySQL and returns the top defects with their score, status, resolution, duplicate link,
resolution note and the best matching chunks. The agents in later milestones can call this function.

## Testing

- Automated tests (`python -m pytest`, folder `backend/tests`) use small synthetic CSV files shaped like the real columns,
  a temporary SQLite database and a test-only word-hash embedder. They check cleaning, chunking, the full build, search,
  metadata filtering and duplicate retrieval.
- `python -m app.kb.evaluate` measures retrieval on the real data: for Apache issues marked as duplicates, it searches with
  the duplicate's text and reports how often the original appears in the top 1, 5 and 10 (recall@k) and the mean reciprocal rank (MRR).
- Mozilla and Eclipse have no duplicate labels, so they are checked by running `python -m app.kb.search` with sample queries and reading the results.

## Known limits

- The automated tests do not use the real datasets or the real embedding model.
- The Apache duplicate link type is assumed to be named "Duplicate" (any link type name containing "duplicate" is accepted).
  The build prints the link type names it found.
- Stack trace detection is pattern-based and can miss unusual formats.
